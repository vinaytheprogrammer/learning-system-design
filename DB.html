SQL, NoSQL & Vector Databases

Three different answers to the same question — where does the data live, and how do you get it back? This guide walks through how each one models data, when to reach for it, the mistakes that show up in production, and the questions interviewers actually ask about them.

01 — The shape of the problem

Same data, three different bets

Every one of these stores the same underlying thing: facts about the world, retrievable later. They differ in what they assume about that data's shape, how far they'll scale a single write pattern, and what kind of question they're fast at answering.

Relational

SQL

Data fits neat tables with known columns. Relationships between tables are explicit and enforced. Optimized for correctness and for asking questions nobody anticipated when the schema was designed.

Non-relational

NoSQL

Data is shaped like the application that reads it — a document, a key, a wide row, a graph. Optimized for horizontal scale, write throughput, and schemas that change weekly.

Embedding-native

Vector

Data is a point in high-dimensional space produced by a model. Optimized for "find me things that mean something similar," not "find me things that match exactly."

Running example used throughout: Atlas Co., a B2B SaaS billing platform. It has customers, orders, support tickets, and a growing pile of historical chat transcripts. We'll model the same business in all three systems so the trade-offs are visible side by side, not abstract.

02 — Relational

SQL databases

Data lives in tables with a fixed set of typed columns. Relationships between tables (a customer has many orders) are declared with foreign keys and enforced by the database itself, not by application code remembering to check.

Atlas Co.'s billing data, modeled relationally

customers
id name plan
1 Atlas Co. Pro
2 Nimbus Labs Free
3 Delta Freight Pro
orders
id customer_id item amount
101 1 API credits $240
102 3 Storage add-on $80
103 1 Support plan $120 
SELECT c.name, o.item, o.amount
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.plan = 'Pro';

Notice Nimbus Labs has no matching row in orders — an INNER JOIN silently drops it. Swap in LEFT JOIN and it comes back with NULL order fields. That silent-drop behavior is a question interviewers love to probe.

ACID, in one line each

  • Atomicity — a transfer debiting one account and crediting another either fully happens or fully doesn't; there's no state where money vanished mid-transaction.
  • Consistency — every transaction moves the database from one valid state to another; a constraint like "balance ≥ 0" can never be violated, even transiently.
  • Isolation — two concurrent transactions don't see each other's half-finished work, as if they ran one after another.
  • Durability — once committed, a power loss the next instant can't undo it; it's on disk (or replicated) for good.

Examples

PostgreSQLOpen-source, extensible (and runs pgvector)
MySQLUbiquitous, read-heavy web apps
SQL ServerMicrosoft stack, enterprise tooling
Oracle DBLegacy enterprise, heavy compliance
SQLiteEmbedded, single-file, mobile/edge
CockroachDBDistributed SQL, geo-replicated ACID

Pros & cons

+ Strong consistency and real multi-row, multi-table transactions
+ Joins and aggregations answer questions you didn't design the schema for
+ Constraints (foreign keys, unique, check) catch bad data at write time
+ Mature tooling: migrations, query planners, decades of operational knowledge
- Horizontal scaling is hard-won (sharding, read replicas, added complexity)
- Schema changes on huge tables need real migration planning
- Rigid shape is a poor fit for data that's naturally nested or ragged
- Vertical scaling has a ceiling, and it costs more per unit near that ceiling
Choose SQL when Correctness and relationships matter more than raw write scale — billing ledgers, inventory, anything with money or regulatory audit trails, and any system where you'll need ad-hoc reporting across entities you haven't thought of yet.

Best practices

  • Normalize to 3NF by default; denormalize deliberately, for a measured read-performance reason — not as the starting point.
  • Index every foreign key and every column that shows up in a WHERE/JOIN/ORDER BY on a large table — but know each index has a write-time cost, so don't index speculatively.
  • Run EXPLAIN ANALYZE on slow queries before guessing at fixes; the planner's actual row estimates usually reveal the real problem.
  • Avoid SELECT * in application code — it breaks the moment someone adds a column, and it ships bytes you don't need.
  • Pick the loosest isolation level that's still safe for the operation; SERIALIZABLE everywhere just trades correctness-worry for throughput.
  • Use connection pooling (PgBouncer, RDS Proxy) — connections are expensive, and an app that opens one per request will starve the database long before CPU does.
  • Watch for N+1 query patterns from ORMs; one query with a join almost always beats a loop of single-row lookups.

03 — Non-relational

NoSQL databases

"NoSQL" is an umbrella over four genuinely different data models. They share one instinct: shape storage around how the application will read the data, and relax the guarantees SQL gives you in exchange for scale and flexibility.

Document — MongoDB, Couchbase

Atlas Co.'s customer record, with its orders embedded right inside it — one read, no join.

{
  "_id": "cust_001",
  "name": "Atlas Co.",
  "plan": "Pro",
  "orders": [
    { "item": "API credits", "amount": 240 },
    { "item": "Support plan", "amount": 120 }
  ]
}
Key-Value — Redis, DynamoDB

A session cache for Atlas Co.'s dashboard — single key, single lookup, sub-millisecond.

GET session:cust_001
> {"userId":"cust_001","role":"admin","ttl":3600}
Wide-column — Cassandra, Bigtable

Order history partitioned by customer, clustered by time — built for relentless writes across many nodes.

PARTITION KEY  customer_id = 'cust_001'
CLUSTERING     order_ts DESC
  2026-10-01   order_103  $120
  2026-09-14   order_101  $240
Graph — Neo4j, Neptune

"Which customers bought what Delta Freight also bought?" — a relationship-heavy traversal, awkward as a SQL join chain.

(Atlas Co.)-[:PLACED]->(Order)-[:CONTAINS]->(Storage)
(Delta Freight)-[:PLACED]->(Order)-[:CONTAINS]->(Storage)

CAP theorem

When a network partition happens — and eventually it does — you can't have perfect consistency and perfect availability at the same time. Click a corner.

Pick a corner

Click Consistency, Availability, or Partition Tolerance to see what you're trading away, and which real systems make that trade.

BASE, not ACID

Most distributed NoSQL stores trade ACID for BASE: Basically Available (the system responds, even if degraded), Soft state (data may change without new writes, as replicas converge), Eventual consistency (reads will reflect the latest write — eventually, not necessarily instantly).

Examples by model

MongoDBDocument, flexible catalogs
RedisKey-value, caching, sessions
DynamoDBKey-value/document, serverless scale
CassandraWide-column, write-heavy at scale
Neo4jGraph, relationship traversal
ElasticsearchDocument + inverted index, search

Pros & cons

+ Horizontal scale is the default posture, not a bolt-on
+ Schema flexes with the application — ship a new field without a migration
+ Very high write throughput (Cassandra, DynamoDB) for logs, events, IoT
+ Natural fit for nested, hierarchical, or graph-shaped data
- Eventual consistency bites you if the app assumes read-your-own-write
- Joins across collections are usually manual, in application code
- Transaction guarantees are improving but still narrower than SQL's
- A bad partition/shard key creates a "hot partition" no amount of scaling fixes
Choose NoSQL when Scale or write velocity dominates (event streams, IoT telemetry, session state), the schema will keep changing, the data is naturally nested or graph-shaped, or you need multi-region availability more than you need a transaction spanning five tables.

Best practices

  • Model for your access patterns first, entities second — in DynamoDB/Cassandra you often design the table around "what query will I run" before "what does the data look like."
  • Choose the partition/shard key for even distribution; a key like status with three possible values creates three hot partitions no matter how many nodes you add.
  • Understand the consistency knobs you actually have (e.g. DynamoDB's eventually- vs strongly-consistent reads, Cassandra's tunable quorum) rather than assuming one default everywhere.
  • Denormalize on purpose and own the duplication — write code (or streams) that keeps copies in sync instead of discovering the drift in production.
  • Set TTLs on ephemeral data (sessions, caches) so cleanup isn't a manual job.
  • Monitor for hot keys/partitions explicitly; they're often invisible until a single node falls over under load.

04 — Embedding-native

Vector databases

A vector database doesn't store rows or documents as the primary unit — it stores embeddings: lists of a few hundred to a few thousand numbers produced by a model, where distance between two points approximates how similar their meaning is. The query isn't "find an exact match," it's "find the nearest neighbors in that space."

Atlas Co., continued: a support agent types "customer says invoice total looks wrong." A keyword search for that exact phrase finds nothing. A vector search finds three past tickets titled "double-charged on renewal," "billing amount doesn't match quote," and "invoice total incorrect" — none sharing the same words, all the same meaning.

Click a point, or run search to place a query
Each dot is a support ticket, embedded into 2D for display (real embeddings run 384–3072 dimensions). Clusters are topics the model learned on its own. Click anywhere to drop a query point — the nearest neighbors light up and connect, ranked by cosine similarity, the way an HNSW index would surface candidates without comparing against every single point.

The vocabulary interviewers expect

  • Similarity metric — cosine similarity, dot product, or Euclidean (L2) distance; which one is "correct" depends on how the embedding model was trained.
  • ANN (approximate nearest neighbor) — scanning every vector for an exact answer doesn't scale past a few hundred thousand rows, so indexes trade a small amount of recall for massive speedups.
  • HNSW — Hierarchical Navigable Small World graphs; layered graphs you "jump" across, landing near the right neighborhood in a handful of hops instead of a full scan.
  • Quantization — compressing vectors (scalar/product quantization) so an index that wouldn't fit in RAM at full precision does, at a small recall cost.

Examples

pgvectorPostgres extension — no new infra
PineconeManaged, serverless, fastest to ship
QdrantRust, self-host or cloud, low latency
Milvus / ZillizDistributed, billions of vectors
WeaviateBuilt-in hybrid search modules
ChromaLightweight, great for prototyping

Pros & cons

+ Finds meaning, not just keywords — the core enabler of RAG and semantic search
+ ANN indexes scale similarity search to billions of vectors in milliseconds
+ Hybrid search (vector + keyword/metadata filter) covers both precision and recall
+ Drop-in for recommendations, dedup, anomaly detection — same core primitive
- Results are approximate; recall@k is a real number you have to measure, not assume
- HNSW graphs are RAM-hungry — the index itself can dwarf the raw vector data
- Swapping embedding models means re-embedding and re-indexing everything
- Younger ecosystem — less standardized than SQL, fewer engineers who've debugged it in production
Choose a vector database when The query is fundamentally "what's similar to this" rather than "what matches exactly this" — RAG pipelines feeding an LLM, semantic search, recommendations, image/audio similarity, or dedup by meaning rather than by hash.

Best practices

  • Match the similarity metric to how the embedding model was trained — most modern text embedding models (OpenAI, Cohere, BGE) are trained for cosine similarity; using L2 against them silently degrades relevance.
  • Start with pgvector if you already run Postgres and you're under ~10M vectors — it adds semantic search without adding an operational system.
  • Tune HNSW's M and efConstruction/efSearch deliberately: higher values buy recall and cost memory/latency — there's no universal default that's right for your data.
  • Measure recall@k against a labeled set before trusting an index's output — "it returns something" isn't the same as "it returns the right thing."
  • Chunk documents with intention (size + overlap) before embedding; a chunk that splits mid-thought embeds a confused, useless vector.
  • Use metadata filters for multi-tenancy and access control, and know whether your engine pre-filters (filter then search, exact but slower) or post-filters (search then filter, fast but can under-return) — it changes correctness, not just speed.
  • Plan for re-embedding: pin your embedding model version, and treat a model upgrade as a migration, not a config change.

06 — Interview prep

Top 10 questions, answered in depth

The ten questions that come up most often across SQL, NoSQL, and vector database interviews — with a real example and the trade-off every answer should surface.

SQL fixes the schema and enforces relationships at write time; NoSQL lets the application define shape and defers (or relaxes) consistency to get scale and flexibility. The decision isn't "which is better" — it's "which failure mode can I tolerate less."

Example

Atlas Co.'s billing ledger goes in Postgres: a debit/credit must never partially apply, and finance needs to join across customers, invoices, and payments for reports nobody specified in advance. Atlas Co.'s activity feed ("Jane viewed the dashboard," millions of events/day) goes in Cassandra or DynamoDB: losing strict ordering under a network blip is fine, but losing write throughput is not.

+ SQL: pick it when being wrong is worse than being slow
+ NoSQL: pick it when being unavailable is worse than being briefly stale

Walk through a money transfer: debit account A $100, credit account B $100. That single business operation is two writes, and ACID is what keeps those two writes behaving as one unit.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
COMMIT;

Atomicity: if the process crashes after the first UPDATE, the transaction rolls back entirely — A never loses $100 without B gaining it. Consistency: a CHECK (balance >= 0) constraint can't be violated by this transaction, even mid-flight. Isolation: a concurrent read of account A won't see the debited-but-uncommitted balance. Durability: once COMMIT returns, a server crash one millisecond later doesn't lose it.

+ Guarantees correctness without the app hand-rolling locks
- Strict isolation levels cost throughput under heavy contention

No — not during an actual network partition. CAP says a distributed data store can only guarantee two of Consistency (every read sees the latest write), Availability (every request gets a response), and Partition tolerance (the system keeps working despite dropped/delayed messages between nodes) — and since partitions are a fact of networked life, the real choice is CP vs AP.

Example

DynamoDB and Cassandra default to AP: during a partition they keep accepting writes on both sides and reconcile later (eventual consistency) — Atlas Co.'s activity feed can be briefly stale, that's fine. A system like a traditional single-leader Postgres cluster with synchronous replication leans CP: if it can't confirm the write landed safely, it refuses the write rather than risk returning a wrong answer.

+ AP: Atlas Co.'s feed stays up during a regional blip, briefly stale
- CP: Atlas Co.'s ledger would rather reject a write than risk double-counting money

Key-value (Redis, DynamoDB) — O(1) lookup by key; Atlas Co. uses it for session tokens and rate-limit counters. Document (MongoDB) — JSON-like, nested; Atlas Co.'s product catalog, where each item has a different set of optional attributes. Wide-column (Cassandra, Bigtable) — partitioned, clustered rows built for massive writes; Atlas Co.'s time-series usage metrics. Graph (Neo4j) — nodes and edges; Atlas Co.'s "customers who bought X also bought Y" recommendation traversal.

+ Each model maps almost 1:1 onto a specific access pattern — pick by query, not by popularity
- Using the wrong model (e.g. graph traversal forced into key-value) fights the engine the whole way

Normalization splits data so each fact lives in exactly one place (3NF: no repeating groups, every non-key column depends on the whole key) — it prevents update anomalies, like a customer's name being stored in 40 order rows and drifting out of sync. Denormalization intentionally duplicates data to avoid a join on a hot read path.

Example

Atlas Co.'s orders table stores only customer_id (normalized) — but the dashboard's "recent orders" view is read a million times a day and joining to customers every time is wasteful, so a materialized order_summary table carries a denormalized copy of customer_name, refreshed on write or on a schedule.

+ Denormalize a specific, measured hot path — not the schema by default
- Every denormalized copy is a place data can silently drift out of sync

Without an index, finding rows matching a condition means scanning every row (O(n)). A B-tree index keeps values in sorted order across a balanced tree, so a lookup walks a handful of nodes — O(log n) — instead of the whole table. It's the same reason a phone book beats reading every name front to back.

Example

CREATE INDEX idx_orders_customer ON orders(customer_id); turns the earlier JOIN from a full scan of orders into a direct lookup per customer. But every INSERT/UPDATE on orders now also has to update that index — and every index beyond it. A table with eight rarely-used indexes pays that write tax eight times over for queries that run once a month.

+ Index the columns your actual slow queries filter, join, or sort on
- Indexing "just in case" quietly taxes every write forever

A traditional database answers "which rows exactly match this condition." A vector database answers "which stored points are geometrically closest to this one" — it stores embeddings (arrays of floats from a model) instead of, or alongside, structured fields, and its core index is built for approximate nearest-neighbor search, not exact lookup.

Example

A keyword search for "invoice total incorrect" in Postgres full-text search finds rows containing those words. A vector search over the same ticket, embedded, also surfaces "double-charged on renewal" — same meaning, zero shared words — because both tickets land near each other in embedding space. 

+ Finds relevant results even when the wording doesn't match at all
- Can't explain "why" a result matched as crisply as a WHERE clause can

Exact nearest-neighbor search means computing the distance from your query to every single stored vector — fine at 10,000 rows, unworkable at 500 million. ANN indexes accept a small, measurable chance of missing the true nearest neighbor in exchange for sub-linear search time.

HNSW builds several layers of a graph: the top layer has few nodes with long-range connections (for big jumps across the space), lower layers are denser (for fine-grained refinement). A search starts at the top layer, greedily moves to the closest neighbor, drops a layer when it can't improve, and repeats — landing near the right neighborhood in roughly log(n) hops instead of n comparisons.

+ Sub-linear query time even at billions of vectors
- Recall is probabilistic — "did it actually find the true nearest neighbor" must be measured, e.g. recall@10, not assumed

An LLM's knowledge is frozen at training time and has no idea about Atlas Co.'s internal tickets. RAG bridges that gap at query time: embed the user's question, use the vector database to retrieve the most semantically relevant chunks of private/current data, and stuff those chunks into the LLM's prompt as context before it answers.

Example

A support agent asks an internal assistant "has anyone seen a double-billing issue like this before?" The pipeline embeds the question, the vector DB returns the top 5 most similar past tickets, and the LLM answers using those real tickets instead of guessing from training data.

+ Lets an LLM answer accurately about private, current, or niche data without retraining
- Answer quality is capped by retrieval quality — garbage chunks in, garbage answer out

This is the question that checks whether you reach for one database out of habit or genuinely pick per workload. A strong answer uses all three, each for what it's good at, and explains why no single store would do.

Example answer — Atlas Co. support platform

PostgreSQL — the system of record for tickets, customers, and SLAs; it needs real transactions (closing a ticket and logging an audit event together) and relational integrity. Redis — caches the logged-in agent's session and recent-ticket list for sub-millisecond dashboard loads. pgvector (or a dedicated vector DB past a few million tickets) — stores embeddings of ticket text so agents can search "has this happened before" by meaning, feeding a RAG assistant that drafts suggested replies. 

+ Each store does the one thing it's actually good at; none is forced outside its strengths
- Three systems means three things to operate, monitor, and keep in sync — justify the complexity against a single-store alternative first
