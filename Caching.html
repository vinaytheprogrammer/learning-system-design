Module 1

Caching Topology & Architecture

Where caches physically sit between a user and a disk, and what that distance costs or saves at each layer.

Cache layers

Every layer answers the same question — "has someone already computed this?" — at a different distance from the user, with a different blast radius when it says no.

What's shown: bar height is relative latency, not to scale — each layer can short-circuit the request on a hit; only a miss at every layer ever reaches the database, which is both the point of caching and exactly what Module 4 is about when that protection fails.

LayerTypical latencyUse caseInvalidation
Client / HTTP0ms (no network)Static assets, rarely-changing responsesCache-Control / ETag, or URL versioning
CDN10–50ms (edge PoP)Global static delivery, edge API cachingPurge API, often eventually consistent across PoPs
Reverse proxy1–5ms (LAN)Offload identical requests before they reach app serversShort TTL or explicit purge (Varnish VCL / nginx)
Application (in-memory)ns–µs (same process)Hot config, per-instance computed valuesLocal only — not shared across instances
Distributed (Redis/Memcached)0.5–2ms (same-AZ network)Shared state across every app instanceExplicit delete/update, Pub/Sub, or TTL

In-memory vs. distributed caches

Local caches (Guava, Ehcache, Caffeine) live on-heap inside one process — zero network cost, but N application instances hold N independent copies, multiplying memory and guaranteeing nothing about cross-instance consistency. Large on-heap caches also feed directly into GC pressure: more live objects means longer stop-the-world pauses, especially during old-generation compaction.

Distributed caches (Redis/Memcached clusters) hold exactly one shared copy, but every read pays network latency plus serialization/deserialization cost, and introduce a failure mode local caches can't have at all: split-brain.

What's shown: without quorum-based fencing (Sentinel/Cluster requiring a majority to accept a primary), both sides can keep serving writes during the partition — the CAP trade-off applies directly to the cache layer, not just the database behind it.

Core trade-off
GC pauses + N× memory
network I/O + split-brain risk

Local caching trades network cost for heap pressure and per-instance duplication. Distributed caching trades that duplication for a network hop and a genuinely distributed-systems failure mode.

Redis vs. Memcached

MemcachedRedis
Memory managementSlab allocation — fixed chunk-size classes, O(1) alloc, internal fragmentation + slab calcification under shifting item sizesjemalloc — general-purpose allocator, dynamic resizing of internal structures, less fragmentation at slightly more allocator overhead
Data structuresOpaque blobs onlyStrings, hashes, lists, sets, sorted sets (skip-list backed, O(log n)), bitmaps, HyperLogLog, streams
Concurrency modelMulti-threaded since early versions — thread-per-core, true parallel get/setSingle-threaded command execution (I/O threading added in 6+) — no locks, every command atomic by construction
Replication / persistenceNone built-in — purely ephemeralPrimary-replica replication, AOF/RDB persistence, Sentinel failover, Cluster sharding

Redis's rich types let the server itself do read-modify-write operations — increment a field, push to a list, pull the top-N of a sorted set — that Memcached would need a full round trip and client-side logic to replicate.

Core trade-off
simpler, multi-core throughput
richer features, single-threaded execution

Memcached scales raw multi-core get/set throughput more easily and predictably. Redis trades some of that for atomic composite operations, persistence, and built-in replication — useful well beyond "just a cache."

Module 2

Cache Strategies & Data Consistency

How data actually moves between the application, the cache, and the system of record — and what breaks when two writers disagree about which value is current.

Caching patterns

PatternRead pathWrite pathConsistencyRisk
Cache-AsideApp checks cache → miss → reads DB → populates cacheApp writes DB, then invalidates cache entryStale window between DB write and invalidationCold-start penalty on first read after a miss
Read-ThroughSame as cache-aside, but the cache owns the loader logicUsually paired with write-throughSame profile as cache-asideLoader logic centralized, not scattered in app code
Write-ThroughStandard cache readWrite to cache, cache synchronously writes DB before ackNo staleness windowEvery write pays cache + DB latency serially
Write-BehindStandard cache readWrite to cache, ack immediately, DB write buffered & asyncFastest write pathData loss if cache crashes before flush

What's shown: the write path only ever touches the cache synchronously — everything after the acknowledgment is the cache's own problem, including the window where a crash loses unflushed writes entirely.

The consistency dilemma & the dual-write problem

A cache is effectively a second, replicated data store living beside the database — CAP applies directly. During a partition, you either serve possibly-stale cached data (favor availability) or refuse to serve until consistency is confirmed (favor consistency). Nearly every real cache deployment picks availability + eventual consistency: if the data genuinely needed strong consistency, it probably shouldn't be cached at all.

The dual-write problem: there's no atomic "write DB and cache together" — you write one, then the other, and concurrent threads can interleave between them.

What's shown: A's correct write (x=2) is silently lost — not because either write was wrong in isolation, but because they interleaved with a stale read in between.

  1. Delete, don't update — invalidate the cache entry on write instead of setting it, so the next read repopulates fresh from the DB rather than trusting whichever write won the race.
  2. Delayed double-delete — delete before the DB write, write DB, delete again after a short delay to catch any read that repopulated from a stale replica mid-write.
  3. Versioning / CAS — attach a version or timestamp to cache writes; reject any write whose version is older than what's currently cached.
  4. TTL as backstop — whatever the race resolves to, staleness self-heals once the TTL expires.

Eviction policies, under the hood

PolicyStructureComplexityWeak point
LRUHash map + doubly-linked list (recency order)O(1) access & eviction; +2 pointers/entryIgnores frequency — one-off scans pollute the cache
LFUFrequency buckets, each an LRU list of keys at that countO(1) access & eviction; more memory than LRUPast popularity resists eviction without a decay factor

What's shown: ghost lists hold no data, only keys — they let ARC learn from near-misses ("this evicted item would have been useful again") and self-tune the recency/frequency balance without a human-set decay parameter.

Module 3

Distributed Caching at Scale

What changes when a cache is partitioned across hundreds of nodes instead of running as one process.

Consistent hashing & virtual nodes

hash(key) % N breaks the moment N changes — a new modulus reassigns nearly every key to a different node, forcing a cache-wide rebuild from the database at exactly the moment you were scaling because load was already high.

Consistent hashing maps both nodes and keys onto the same ring (e.g. a hash space of 0 to 232−1). A key belongs to the first node found walking clockwise from its position. Adding or removing a node only moves the keys between it and its clockwise neighbor — roughly 1/N of the keyspace, not all of it.

What's shown: each physical node holds several virtual nodes scattered around the ring instead of one point — without this, a handful of physical nodes placed directly on the ring produce uneven arc sizes (data skew) purely by hash-position luck. With ~100–200 virtual nodes per physical node, each one's total share converges to a fair 1/N.

Cache invalidation across data centers

MechanismDelivery guaranteeLatencyBest for
TTLNone needed — no coordination at allBounded by TTL windowSimplicity; accepts staleness up to the TTL
Redis Pub/SubFire-and-forget — a disconnected subscriber misses the message permanentlyNear-instant, same regionBest-effort, single-region invalidation
Kafka / RabbitMQDurable, replayable — consumers resume from last offsetHigher — write to broker, then consumeCross-data-center propagation where delivery must eventually happen

What's shown: many systems run both — Pub/Sub for near-real-time same-region invalidation, Kafka as the durable system of record ensuring every region eventually gets the message even after an outage.

Hotspot mitigation

A celebrity tweet or flash-sale item can push one key's traffic far beyond what one shard can serve, even while the rest of the cluster sits idle. Consistent hashing guarantees even key distribution, not even traffic distribution — a hot key always lives on exactly one shard, no matter how many shards exist.

What's shown: write amplification (N writes instead of 1) is a fine trade for a read-heavy hotspot, which is the overwhelmingly common shape.

  • Local/L1 layer — cache the hot value in each app instance's memory with a short TTL, converting most traffic into zero-network local reads.
  • Read replicas — add replicas behind the hot shard specifically, spreading reads across multiple physical nodes.
  • Key salting — as shown above; the standard fix for read-heavy single-key hotspots.
Detection trap

Aggregate per-shard metrics can look perfectly healthy while one key inside a shard saturates its ingress. Spotting this requires per-key traffic sampling (Redis MONITOR, client-side sampling) — not just shard-level CPU/network dashboards.

Module 4

Failure Modes & Resiliency

The three catastrophic cache failures interviewers reach for first — because they separate "has read about caching" from "has been paged for it."

Cache avalanche

Two distinct mechanics share the name. Mass simultaneous expiry: many keys set with identical TTLs (a bulk warm job, a deploy) expire together, sending a synchronized wave of misses at the database all at once. Cluster crash: the entire cache goes down and every request that would have hit now falls straight through — not a wave, a cliff.

Mitigations: uniform random TTL jitter spreads expiry (shown above) for the "mass expiry" mechanic. Circuit breakers that trip on cache error-rate/latency thresholds — stopping the app from hammering a dead cache and shedding or degrading requests instead — address the "cluster crash" mechanic. A local L1 layer (Module 1) can keep serving reads even while the distributed cache is fully down.

Cache penetration

A request for a key that exists in neither the cache nor the database is a guaranteed miss every single time — there's nothing to cache. An attacker (or a buggy client) hammering non-existent IDs bypasses the cache's protection entirely and floods the database directly, no matter how well the cache is tuned for real keys.

  • Cache the null result — store "not found" with a short TTL so repeated requests for the same missing key hit the cache instead of the DB. Doesn't help if the attacker varies the key every time.
  • Bloom filter in front — a probabilistic set of every key known to actually exist. "Definitely not present" rejects the request before touching cache or DB at all.
// before touching cache or DB at all
if (!bloomFilter.mightContain(key)) {
    return notFound(); // zero cache, zero DB hit
}
// bloom filter: no false negatives, tunable false-positive rate
// (trades memory/hash-count for how often a real-looking miss still reaches the DB)

Bloom filters never produce a false negative — a key that truly exists always passes — but can produce false positives, tunable via filter size and hash-function count. That's enough to stop even randomized-key attacks, since most non-existent keys get rejected before touching anything real.

Cache stampede (thundering herd)

A single, very popular key expires. In the instant after, potentially thousands of concurrent requests all miss simultaneously and all independently recompute the same value from the database — one expiring key becomes a DB-crushing burst of entirely redundant work.

What's shown: the first request to notice the miss acquires a lock (Redis SETNX) and is the only one allowed to recompute; everyone else waits briefly and reads the result it just populated — named after Go's singleflight package.

Probabilistic early expiration (XFetch): instead of waiting for hard expiry, each read gets a small, rising chance of proactively recomputing the value before it expires — scaled by how close the key is to expiry and how expensive recomputation is. This staggers recomputation across many different moments so the herd never fully forms, with no locking required at all.

Mutex vs. probabilistic
coordination + wait (hard guarantee)
no locking (statistical reduction)

SingleFlight gives a hard guarantee (exactly one DB hit) at the cost of a lock and a wait for followers. XFetch needs no coordination but only statistically reduces stampede risk, and requires per-key metadata alongside the cached value.

Module 5

Advanced Engineering & Hardware Realities

The layer below the layer — where caching stops being a design pattern and starts being physics.

CDN edge computing

Cloudflare Workers and Lambda@Edge run actual application logic at CDN points of presence, not just serving static bytes. This enables dynamic cache-key construction (vary by geo/segment/device without a full cache-per-user explosion), request/response rewriting before or after the cache layer, personalization without a round trip to origin, and edge-side auth checks that reject invalid requests before they ever reach origin.

The architectural shift is real: a CDN used to be a dumb static-blob store. Edge compute turns it into a programmable tier that makes caching decisions, not just serves cached bytes — blurring the line between CDN, reverse proxy, and application layer, and pushing logic as close to the user as physically possible.

Low-level caching: the hardware underneath

What's shown: even the fastest NVMe is still 100–1000× slower than RAM for a single random access — this gap is the entire reason in-memory caching exists as a category.

False sharing: two unrelated variables that happen to land in the same 64-byte CPU cache line, written by different cores, force the whole line to bounce between cores' caches on every write under the cache-coherency protocol — silently destroying parallelism that should have been free. Fixed by padding/alignment so independent hot variables get separate lines.

OS page cache: the kernel transparently caches recently-read disk pages in otherwise-unused RAM — this is why a second read of the same file is dramatically faster with zero application-level caching code, and why "available memory" on a healthy Linux box often looks almost fully used.

Monitoring & metrics

MetricWhat it meansWatch for
Hit ratiohits / (hits + misses)Context-dependent — >95% for static CDN content, 60–70% can be healthy for personalized workloads. Watch the trend, not the absolute number.
Eviction rateEntries evicted from memory pressure, not TTL/explicit invalidationRising on stable traffic = memory-constrained, a leading indicator of hit-ratio collapse before it shows up there
Memory fragmentation ratioOS-reported memory / allocator-reported used memory>1 means the allocator holds more physical memory than the data needs; <1 can indicate swapping
Latency p99 / p99.9Tail latency, not the meanGC pauses, network blips, and miss-triggered DB fallback all hide inside the tail — never monitor caching on the average alone
Staff-level instinct

Average latency hides exactly the problem caching exists to solve. A cache with excellent mean latency can still have a p99.9 dominated by GC pauses or cold-path DB fallback — user-perceived pain lives in the tail, so that's what gets paged on.
