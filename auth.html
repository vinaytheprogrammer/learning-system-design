Module 1

Advanced Identity & Authentication

How identity is proven once, and kept proven, across a system with no single memory.

Stateless vs. stateful auth

A stateless token (JWT, Paseto) is self-contained and signed — any node verifies it alone, with zero shared infrastructure and zero lookup latency. A stateful session stores the truth server-side (Redis/Memcached cluster) and hands the client only an opaque ID; every request pays a cache round trip to ask "is this still valid, and what does it mean right now."

What's shown: identical request shape, different cost structure — the stateless path never leaves the service process; the stateful path pays a cache round trip on every single request in exchange for a server-side source of truth.

JWT / Paseto (stateless) Session store (stateful)
Revocation Hard — valid until expiry unless you add state back Instant — delete the key
Scale-out Trivial — any node verifies alone Needs a shared cache reachable from every node
Payload Self-contained, travels on every request Small opaque ID only
Consistency Claims are frozen at issue time — can go stale Always reflects current server state
Core trade-off — latency vs. consistency
0 lookups
1 lookup / request

Stateless buys zero-lookup horizontal scale at the cost of real-time control. Stateful buys perfect, instant control at the cost of a shared dependency every node must reach.

Staff-level default

Hybrid: short-lived (5–15 min) stateless access token + a stateful, revocable refresh token. Worst-case blast radius after compromise is bounded by the access token's TTL, not by how fast you can purge a cache.

Token mechanics: JWT structure & key distribution

A JWT is three base64url segments joined by dots: header.payload.signature. The payload is encoded, not encrypted — anyone can read it. Only the signature is cryptographic protection, and it protects integrity, not confidentiality.

What's shown: only the auth server ever touches the private key. Every other service verifies with a freely-distributable public key, matched by the header's kid — which is exactly what makes RS256 viable across many independent microservices.

HS256 trap

HS256 is symmetric — the same secret signs and verifies. Every verifying service needs that secret, so compromising any one of them lets an attacker forge tokens for the whole system. Fine inside one trust boundary; wrong the moment a second team or third party needs to verify tokens.

ES256 (ECDSA) is a common third option: asymmetric like RS256, with smaller signatures and faster verification — increasingly preferred for size-sensitive or high-throughput edges.

The token revocation problem

A stateless token is valid by math until it expires — there's no built-in "ask the server" step. Compromise response time is bounded by token TTL, unless you deliberately add state back in.

What's shown: each refresh is single-use. Reuse of an already-rotated refresh token means someone else has a copy — the fix is to kill every token descended from that family, not just the one reused.

Approach Mechanism Cost
Blacklist Store revoked jti in Redis until natural expiry; gate the check behind a Bloom filter if read volume is extreme Checked on every request
Short TTL + rotation 5–15 min access tokens; single-use, rotating, stateful refresh tokens Checked only at refresh time
Staff-level default

Rotation handles routine revocation with far less lookup traffic. Reserve a blacklist for the "kill this session right now" emergency path — often just a per-user "issued-before" cache entry rather than tracking individual token IDs.

Modern MFA

All three prove "something you have," but they differ in exactly what can leak and to whom.

Method Mechanism Core weakness
SMS OTP Code delivered over the telecom network SIM-swap & SS7 interception — NIST 800-63B marks it "restricted"
TOTP Both sides independently compute HMAC-SHA1(shared secret, time step) Shared secret exists in two places — a server-side leak forges every code
FIDO2 / WebAuthn On-device key pair; private key never leaves hardware; server stores only the public key Phishing-resistant — signature is bound to the origin at the protocol level

A fake lookalike login page can relay a TOTP or SMS code to the real site in real time — the user never notices. It cannot do this to FIDO2: the browser binds the signature to the actual origin, so a phishing domain simply gets a signature that's useless anywhere else. This is the mechanism behind Passkeys.

Cryptographic hashing for password storage

Algorithm Hardness lever Resists
bcrypt Cost factor doubles rounds per increment (2^cost); ~4KB memory Brute force, weakly — tiny fixed memory makes GPU/ASIC parallelism cheap
scrypt Tunable memory parameter (N, r, p) GPU/ASIC parallel cracking — memory cost scales per attempt
Argon2id Independently tunable memory, time, parallelism Both side-channel timing attacks (Argon2i half) and GPU cracking (Argon2d half) — current OWASP default

Salts are random, unique, non-secret values stored alongside each hash — they defeat precomputed rainbow tables and guarantee two identical passwords hash differently. The work factor is tuned against your own hardware: roughly 200–500ms per hash is negligible for one real login, but devastating for an attacker running billions of guesses.

Module 2

Protocols & Delegated Access

How identity gets federated across organizational boundaries without every party trusting every other party directly.

OAuth 2.0 grant types & the PKCE exchange

Authorization Code + PKCE is the default for anything with a user and a browser or mobile app. Client Credentials is for service-to-service calls with no user at all — the client authenticates as itself. Implicit Grant returned the access token directly in a URL fragment with no exchange step, leaking into browser history and referrer headers with no way to bind the token to the requesting client — OAuth 2.1 removes it entirely now that PKCE covers the same use case safely.

Why it's safe if the code is intercepted: only the SHA256 hash of the verifier ever travels over the network (step 3). An attacker holding the authorization_code alone cannot produce the plaintext verifier needed at step 5 — stealing the code without stealing the client's memory gets them nothing.

OpenID Connect: identity layered on authorization

OAuth 2.0 answers "what can this app do on my behalf" — it was never designed to answer "who is this user." OIDC adds exactly one new primitive on top: the ID Token.

Token Format Consumed by Purpose
ID Token Always a signed JWT The client application itself "Who logged in" — never sent to an API
Access Token Opaque or JWT Resource servers / APIs "What they can call"
Refresh Token Opaque, long-lived, stateful The authorization server only Get new tokens without re-prompting login
Classic interview trap

Using an ID Token as a bearer token against an API. ID Tokens aren't meant to be validated by arbitrary downstream services and are often not even audience-scoped for that — the ID Token proves identity to the client, the Access Token proves authorization to a resource server. Conflating them is a real vulnerability class, not just a style error.

Token exchange & federation

A user authenticates through Google, Okta, or Apple — internal microservices should never parse that third-party token directly: wrong audience, wrong signing keys, and every service would need its own OIDC discovery logic against an external provider.

What's shown: every downstream service trusts exactly one issuer and one JWKS endpoint — your own — regardless of how many external IdPs the business supports. This is RFC 8693 Token Exchange in practice, and it's the same pattern that lets a B2B SaaS support a dozen enterprise SSO providers without a dozen validation code paths downstream.

Module 3

Enterprise-Scale Authorization

How a system decides "can this specific caller do this specific thing" — reliably, auditably, and inside a single-digit-millisecond budget.

Access control models: RBAC, ABAC, ReBAC

Model Schema Evaluation Weak point
RBAC users, roles, role_permissions, user_roles O(1)-ish set lookup once roles are cached Context-free — "editor" can't mean "editor of exactly these 3 projects" without a role explosion
ABAC None fixed — policies evaluate attribute bags (subject, resource, action, environment) Scales with policy complexity, not table size "What can this user actually do" becomes a computed answer, not a stored one — harder to audit
ReBAC Relationship tuples / graph edges Graph reachability traversal, potentially many hops Naturally expresses nested, inherited sharing (Drive/Docs-style) that the other two do awkwardly

Example ABAC rule in plain language: allow if user.department == resource.department AND time.hour is between 9 and 17. Example ReBAC chain: User A can view Doc X because A is a member of Team B, and Team B owns Folder Y, and Folder Y contains Doc X — three hops, none of which RBAC can express without flattening into per-resource roles.

Google Zanzibar & ReBAC at global scale

Relationships are stored as tuples: object#relation@subject, e.g. doc:X#viewer@team:B#member. A permission check becomes a graph traversal across these tuples — and Zanzibar answers that traversal in single-digit milliseconds at planet scale using four techniques together, not one.

What's shown: the honest three-hop graph walk is correct but slow; a precomputed, asynchronously-rebuilt reverse index turns the common case into a fast lookup. Both paths are evaluated "as of" a consistency snapshot token, not strict real-time global state.

  1. Caching — check results are cached by (subject, relation, object) plus a consistency token.
  2. Consistency snapshots ("zookies") — every check runs against a specific logical timestamp, so reads can be served from a slightly-stale, locally-cached snapshot instead of paying for global consensus per request.
  3. Precomputed reverse indexes — deeply nested membership is flattened asynchronously so deep checks don't walk the live graph every time.
  4. Fan-out evaluation — a check decomposes into parallel sub-checks (path 1 OR path 2 OR …), first-true-wins.
Core trade-off — consistency vs. hot-path latency
strict real-time
bounded staleness

A permission revoked this millisecond might still pass a check elsewhere for a few hundred milliseconds. That's the deliberate price of serving authorization checks inside the request hot path at planet scale — the same stateless-vs-stateful tension from Module 1, one layer up the stack.

Policy as code: OPA & Rego

Pull "if/else" authorization logic out of application code entirely. The app asks a question with a JSON input; OPA answers true/false by evaluating a declarative Rego policy against it — one language, one test suite, one review process, independent of what language the calling service is written in.

# input: { "method": "GET", "user": {...}, "resource": {...} }
package authz

default allow = false

allow {
    input.method == "GET"
    input.user.role == "viewer"
    input.resource.owner == input.user.team
}

Deployment pattern: OPA runs as a sidecar local to each service — low latency, no network hop per check — while policy bundles are pushed centrally. That combination is the point: centralized policy, local evaluation, without a network round trip or logic duplicated across every service's own language.

Module 4

Microservices Architecture & Gateway Patterns

How auth decisions actually travel through a distributed network, instead of staying a diagram.

Edge authentication: the API Gateway

The gateway terminates TLS once, extracts the bearer token, and validates its signature statelessly — no call to the auth server per request.

What's shown: this is the practical payoff of RS256 from Module 1 — the gateway only ever needs public keys, which is exactly what a JWKS endpoint publishes. Nothing invalid ever reaches a downstream service at all.

Downstream context propagation

Once validated at the edge, the gateway has to tell internal services who the caller is — without those services re-validating a full JWT, or worse, trusting an unsigned header blindly.

Dangerous default

A plain X-User-Id header. If any internal network path is reachable without going through the gateway — a very common mistake as systems grow — anyone can forge that header and impersonate any user.

Staff-level default

Forward a signed, internally-scoped context token (or the re-signed original claims). Forging it now requires forging a signature, not sending a string. Network boundaries erode as new services and ingress paths get added over years — header-trust doesn't survive that; cryptographic verification does.

Mutual TLS: service-to-service identity

mTLS answers a different question than everything else in this document: not "which user is this" but "which service is this, and should it even be talking to me." Each side presents a certificate during the handshake and verifies the other's — not just client-verifies-server like ordinary HTTPS.

What's shown: in a mesh like Istio, application code never touches TLS — it calls localhost, and the sidecar handles cert issuance, rotation, and mutual verification transparently.

Interview distinction

mTLS and end-user auth solve orthogonal problems and are normally both present. mTLS proves "orders-service really is orders-service"; propagated context (above) proves "this call is on behalf of user 482." A compromised service with valid mTLS certs still only has its own service identity's permissions — it doesn't inherit arbitrary user identities just by being on the mesh.

Module 5

Threat Modeling, Vulnerabilities & Edge Cases

Where the mechanisms above actually fail, and the traps interviewers build around that failure.

Token storage security

Storage XSS exposure CSRF exposure
LocalStorage Full — any JS on the page can read it, no expiry, persists across tabs/restarts N/A — not auto-attached
SessionStorage Full — same JS-read exposure, cleared on tab close only N/A — not auto-attached
httpOnly + Secure + SameSite=Strict cookie None — invisible to JavaScript entirely Mitigated — not attached cross-site

httpOnly is the single biggest lever against token theft via XSS — a successful injection still can't read the cookie. Secure forces HTTPS-only transmission. SameSite=Strict (or Lax for some flows) is the primary CSRF defense, stopping the cookie from riding along on cross-site requests.

Remaining gap

httpOnly stops token exfiltration, not all XSS impact — a successful injection can still ride the user's authenticated session in real time to make requests. Pair with a CSRF token (double-submit or synchronizer pattern) for state-changing requests as defense in depth, since SameSite enforcement varies across top-level navigations and older clients.

Attack vectors & mitigations

  • Session hijacking & replay — a stolen token or session ID is reused. Mitigated by short TTLs and rotating refresh tokens with replay detection (Module 1.3): the moment a stolen-but-unused refresh token collides with the legitimate client's own use, the whole family is revoked.
  • Credential stuffing & brute force — automated login attempts from leaked credential lists. Rate limit the auth endpoint specifically, by both IP and account: per-IP alone is defeated by botnets and residential proxies; per-account alone allows distributed low-and-slow attempts. Add exponential backoff, CAPTCHA after N failures, and check new credentials against known-breach databases at signup/change time — not just rate-limit the symptom.
  • Confused deputy — a highly-privileged service is tricked by a lower-privileged caller into misusing its own ambient privilege on the caller's behalf. The fix is always propagating the originating caller's scoped identity through every hop (Module 4.2) so the privileged service can tell "acting on my own authority" from "acting on behalf of someone who shouldn't have access."

What's shown: without the originating identity attached to the request, Service A's own broad privilege becomes anyone's privilege the moment they can reach Service B.

TOCTOU: time-of-check to time-of-use

Permission is checked once at request start, then a long-running job runs for 30 seconds — during which an admin revokes that exact permission. The job finishes and commits a side effect the user is no longer allowed to perform, because nothing re-checked between check and use.

What's shown: the race window is everything between the two dots — revocation lands inside it but has no effect because nothing was listening.

  1. Re-check immediately before the side-effecting action, not just at request entry — doesn't close the window, shrinks it to near-zero.
  2. Decompose long work into short, idempotent, independently-authorized steps.
  3. Issue capability-scoped, short-lived tokens for that one operation, timed to expire before a plausible revocation could land.
  4. Version-stamp permissions; validate the version hasn't changed at commit time, and fail safe (force a retry) if it has.
Core trade-off — latency vs. correctness
never re-check
re-check constantly

Eliminating the race entirely costs either constant re-checking (latency) or decomposition and versioning (complexity). The honest staff-level answer is naming the race window you've chosen to accept, sized to the actual risk of the operation — not claiming to have solved it perfectly.
