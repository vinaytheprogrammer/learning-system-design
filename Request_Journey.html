The Request's Journey

Network traffic · eleven concepts, one request

Everything a request passes through before it's answered

A browser tab asking for a web page touches most of these on the way — a name lookup, maybe a tunnel, an address rewrite, a gate, a dispatcher, a front door, and sometimes a smaller version of the same idea inside the code that finally answers. Laid out here in the order a request actually meets them, not alphabetically.

DNS· Proxy· Forward Proxy· VPN· NAT· Firewall· Load Balancer· Reverse Proxy· Nginx· API Gateway· Facade Pattern

Read it left to right: a name gets resolved, the client's own traffic may detour through a proxy or VPN, an address gets rewritten at the network edge, a firewall decides what's even allowed in, a load balancer and reverse proxy decide which machine answers, and an API gateway decides which service handles it. The facade pattern is the same front-door idea, just drawn in code rather than on a wire.

Before the request even starts

DNS — Domain Name System

Translates a domain name into the IP address the client actually needs to open a connection. It's a delegated hierarchy: a resolver asks a root server who's responsible for .com, then asks that TLD server who's responsible for the exact domain, then asks that authoritative server for the address.

What's shown: four hops happen before the browser can even open a connection to the real server — each one cacheable, which is why most lookups skip straight to a cached answer instead of walking the whole chain.

Example: You type example.com. Your resolver has no cached answer, so it asks a root server who handles .com, asks that server who's authoritative for example.com, and asks that server directly — which replies with 93.184.216.34. Only then does your browser open a connection to that address.

Current state

Plaintext DNS lets anyone on the network see every domain you look up. Encrypted DNS (DoH/DoT) has been closing that gap — combined adoption reached roughly 12% of queries by mid-2026, and Firefox now defaults to DoH for most U.S. users, with Chrome, Edge, Windows, and macOS all supporting it natively.

Strengths

  • Lets names stay stable while the IPs behind them change — failover, migrations, and scaling need no client changes.
  • Heavily cacheable at every layer, so the full chain is rarely walked in practice.
  • Delegated hierarchy means no single server has to know the whole internet.

Weaknesses

  • Adds a round trip before the real request starts (hidden by caching most of the time).
  • Unencrypted DNS exposes browsing activity to anyone on the network path.
  • A frequent target for cache poisoning and DDoS given how load-bearing it is.
Reach for it

It isn't optional — every request needs it. What you actually choose is the resolver and whether it's encrypted (DoH/DoT) and signed (DNSSEC).

The general idea

Proxy

A proxy is any intermediary that relays a request on someone's behalf instead of letting the two ends talk directly. The two specific flavors below differ only in whose identity it's fronting: a forward proxy stands in front of the client, a reverse proxy stands in front of the server.

What's shown: same mechanism, mirrored. One hides the client from everything past it; the other hides the server from everything in front of it. Both get their own section below with real examples.

Fronts the client

Forward Proxy

Sits in front of a client (or a whole fleet of them), forwarding their requests out to the internet. The destination only ever sees the proxy's address — never the original client's.

What's shown: the proxy node swaps between its two jobs — filtering/logging the request, then presenting it to the outside world with its own IP in place of the client's.

Example: A company routes every employee laptop's web traffic through a corporate forward proxy. IT can block categories of sites and cache common downloads for everyone; any external site the employee visits sees the proxy's IP, never the laptop's.

Strengths

  • Hides the client's real IP and identity from the destination.
  • One place to enforce content filtering, logging, and caching for many clients at once.
  • Can route around geographic or network-level restrictions.

Weaknesses

  • A bottleneck and single point of failure for everyone behind it.
  • Needs client-side configuration, or transparent network interception, to actually take effect.
  • The proxy operator sees everything — a trust concentration point.
Reach for it

When you need to control or anonymize outbound traffic for a group of clients you manage — corporate and school networks are the classic case.

A forward proxy, encrypted

VPN — Virtual Private Network

Tunnels all of a device's traffic, encrypted, to a remote VPN server, which then forwards it on. The encryption is the key addition over a plain forward proxy — and the tunnel also gives the device a virtual presence on a private network it couldn't otherwise reach.

What's shown: the marching dashes are the encrypted tunnel — everything between laptop and gateway is unreadable to anyone watching the network in between, including on untrusted public Wi-Fi.

Example: A remote employee starts a WireGuard connection before opening the internal payroll system, which has no public DNS entry at all. The VPN gateway is the only way in; once connected, the laptop behaves as if it were plugged into the office network.

Current state

Most mid-to-large organizations are shifting the bulk of remote access to Zero Trust Network Access (ZTNA), which grants per-application access after checking identity and device posture on every connection, rather than dropping a device onto the whole network. A narrowly scoped VPN typically remains only for the handful of things that genuinely need raw network-level reach.

Strengths

  • Encrypts all traffic to the VPN server — safe even on hostile networks.
  • Gives a remote device reach into resources that were never exposed publicly.
  • One connection covers every app on the device, not just the browser.

Weaknesses

  • Grants broad network-level access by default — a compromised device reaches everything the VPN exposes.
  • Adds latency since every packet detours through the VPN server.
  • A high-value target: VPN gateways are a common entry point in real breaches.
Reach for it

To reach resources that are genuinely private, or to encrypt traffic on an untrusted network — increasingly as a narrow complement to ZTNA rather than the whole remote-access story.

At the network boundary

NAT — Network Address Translation

Rewrites the source (or destination) address of packets as they cross a network boundary, letting many private IP addresses share one public one. Your home router does this for every device on your Wi-Fi, right now.

What's shown: three private addresses funnel through one public address; the router remembers which internal device owns which outbound connection so replies land on the right laptop.

Example: Your laptop at 192.168.1.14 requests a web page. Your router rewrites the source to its own public IP and records the mapping; the reply comes back addressed to the router, which looks up the table and forwards it to your laptop specifically.

Current state

Because the world ran out of spare IPv4 addresses, most ISPs now also run Carrier-Grade NAT — NAT-ing an entire customer base behind a small pool of public IPs; over two-thirds of Tier-1 ISPs run it. IPv6, which needs no NAT, carries roughly 46% of traffic as of early 2026, but full IPv4 retirement isn't expected before 2030, so NAT stays load-bearing for a long time yet.

Strengths

  • Lets a whole network share one scarce public IPv4 address.
  • Incidentally hides internal topology from the outside.
  • Transparent to applications — no client-side changes needed.

Weaknesses

  • Breaks the assumption that every device has its own reachable address, forcing workarounds like STUN/TURN for peer-to-peer and video calls.
  • The translation table is extra state the router must maintain — a failure point.
  • Carrier-grade NAT in particular can make abuse hard to trace to one customer.
Reach for it

Essentially mandatory anywhere private IPv4 space meets the public internet — home routers, cloud VPC egress, carrier networks — until IPv6 is ubiquitous.

At the network boundary

Firewall

Inspects traffic crossing a boundary and allows or blocks it against a rule set — by IP, port, and protocol, or, for modern "next-gen" firewalls, by the actual application and content.

What's shown: HTTPS on 443 is on the allow list and passes straight through; an RDP attempt on 3389 isn't, and bounces off the rule set entirely.

Example: A data center firewall allows inbound 443 to the web tier, allows 22 (SSH) only from the office's IP range, and denies everything else by default — shrinking what's reachable from the internet to exactly two intentional openings.

Strengths

  • Shrinks the attack surface to only the ports and protocols actually needed.
  • Can be layered — perimeter, between internal tiers, and per host — for defense in depth.
  • Modern versions inspect encrypted-traffic metadata and known attack signatures.

Weaknesses

  • Rule sets drift and accumulate unintended holes over time.
  • Does nothing about an attack riding on an already-allowed port.
  • A purely perimeter firewall does nothing once an attacker is already inside.
Reach for it

At every boundary as a baseline — perimeter, between tiers, on hosts — but treat it as a floor, not the whole security story.

Fronts many backends

Load Balancer

Spreads incoming requests across multiple backend servers so no single one is overwhelmed, and stops sending traffic to any that fail a health check. Works at L4 (routes by IP/port, doesn't look inside the packet) or L7 (routes by URL, header, or cookie).

What's shown: traffic alternates between the two healthy servers; the one failing its health check is pulled out of rotation automatically until it recovers, with no client ever noticing.

Example: A shopping site runs six identical backend instances behind a load balancer using "least connections," with a health check pinging each instance every 5 seconds — an instance that stops responding is pulled out of rotation immediately, not after users start seeing errors.

Strengths

  • Removes any one server as a single point of failure.
  • Scale horizontally by adding instances behind the same address.
  • Enables zero-downtime deploys by draining and replacing instances one at a time.

Weaknesses

  • Becomes itself a single point of failure unless deployed redundantly.
  • Adds a hop, and for L7, decrypt/re-encrypt overhead.
  • Naive algorithms can still overload an instance if request cost varies a lot.
Reach for it

As soon as there's more than one instance of anything — something has to decide which instance gets each request.

Fronts the server

Reverse Proxy

The mirror image of a forward proxy: sits in front of one or more backend servers, accepting client requests and forwarding them to the right one. Clients only ever see the reverse proxy's address — the real servers behind it stay private.

What's shown: three app servers live behind the proxy on a private network with no direct route in from the internet — the public surface area is exactly one address, the proxy's.

Example: nginx sits in front of three application servers. Clients only ever talk to nginx's public IP, which terminates TLS and forwards the plain request internally — the app servers themselves have no public IP at all.

Strengths

  • Hides backend topology and IPs from the outside entirely.
  • One place to centralize TLS termination, caching, and compression instead of in every backend.
  • Backends can be added, removed, or replaced with zero visible change to clients.

Weaknesses

  • Adds a hop and a piece of infrastructure that itself must stay available.
  • A misconfiguration here affects every backend behind it at once.
  • One more place to manage TLS certificates.
Reach for it

Any time you want one stable public address in front of backends that may change, scale, or need to stay private.

A concrete implementation, not a new idea

Nginx

Nginx isn't a separate concept — it's the single most common piece of software that actually implements several of the roles above at once: web server, reverse proxy, load balancer, and, via F5's commercial line, API gateway. One configuration file plays all three roles below.

# three roles, one config file
upstream app_servers {
    least_conn;
    server 10.0.1.10:3000;
    server 10.0.1.11:3000;
    server 10.0.1.12:3000;
}

server {
    listen 443 ssl;
    server_name shop.example.com;

    location / {
        proxy_pass http://app_servers;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
upstream + least_conn → load balancer proxy_pass → reverse proxy listen 443 ssl → TLS termination / web server
Current state

F5's NGINX Plus 37.0 (2026) added agentic-traffic monitoring, a remote configuration API, and high-fidelity upstream latency metrics. The open-source core stays free and remains the default most teams reach for; F5's commercial tier adds the dynamic reconfiguration and API-gateway features larger enterprises pay for.

Strengths

  • Event-driven, non-blocking architecture handles tens of thousands of concurrent connections on modest hardware.
  • One tool covers web serving, reverse proxying, load balancing, and basic caching.
  • Enormous community, documentation, and hosting-provider support.

Weaknesses

  • Open-source config is static/file-based — dynamic reconfiguration needs the paid tier or extra tooling.
  • Config syntax has a learning curve; a missing directive like proxy_set_header is a classic silent bug.
  • Deep API-management features (auth, rate limiting per consumer) aren't native to the open-source core.
Reach for it

The default choice when you need a reverse proxy, load balancer, or web server and want one well-understood, battle-tested tool instead of assembling several.

A reverse proxy, specialized for APIs

API Gateway

A reverse proxy purpose-built for APIs: on top of routing and TLS, it typically owns authentication, rate limiting, and request transformation — one consistent front door for many backend services.

What's shown: the same gateway runs every request through auth and rate-limit checks before routing — checks that would otherwise have to be duplicated inside every single backend service.

Example: A mobile app calls api.example.com/orders. The gateway validates the caller's JWT, confirms they're under 100 requests/minute, and forwards to the internal orders-service — the same gateway does the identical auth/rate-limit dance for a dozen other services behind it.

Current state

Kong remains the most widely deployed self-managed gateway, with a 200+ plugin ecosystem. Envoy has become the de-facto proxy layer inside service meshes like Istio — usually run as a sidecar rather than configured directly. Cloud-managed options like AWS API Gateway bill per request rather than per server.

Strengths

  • Centralizes auth, rate limiting, and request shaping instead of duplicating it in every service.
  • Gives external consumers one stable, versioned surface even as internal services churn.
  • A natural point to add caching, validation, and analytics.

Weaknesses

  • Every request flows through it — an outage there takes down everything behind it.
  • Adds latency per hop and one more system to operate and scale.
  • Can accumulate enough business logic to become a hidden, hard-to-test monolith.
Reach for it

Once there's more than a couple of backend services behind one public API, or auth/rate-limiting/versioning needs to be consistent without repeating it everywhere.

The same idea, one altitude lower

Facade Pattern

A software design pattern, not infrastructure: one class that gives a simple, high-level interface over a complicated subsystem of smaller classes, so callers don't need to know how it's wired together inside.

What's shown: client code calls exactly one method; the facade is the only thing that knows four other classes even exist, let alone how to orchestrate them.

Example: VideoConverterFacade.convert(file, format) internally coordinates a codec factory, a bitrate reader, an audio mixer, and a video writer — calling code never touches any of those four classes directly.

Why it's on this list

It's the same shape as a reverse proxy or an API gateway — hide a messy, multi-part system behind one simple, stable entry point — just applied inside a codebase instead of across a network.

Strengths

  • Decouples callers from the subsystem's internals, so it can be refactored freely behind a stable interface.
  • Makes a complex library approachable with a minimal surface area.
  • A natural seam for testing — mock the facade, not a dozen classes.

Weaknesses

  • Can turn into a "god object" that attracts unrelated responsibilities over time.
  • Power users who need lower-level access get forced into awkward escape hatches.
  • One more layer of indirection to read through when debugging.
Reach for it

When a subsystem has grown complex enough that most callers only need one or two high-level outcomes from it — the same instinct as a reverse proxy, applied inside a codebase.

The mental map

Concept Sits in front of Hides / protects Example
DNS — (name resolution) nothing — a lookup 1.1.1.1, Route 53
Forward Proxy the client client identity/IP Squid, corp proxy
VPN the client (encrypted) client traffic + identity WireGuard, OpenVPN
NAT the network boundary internal address space home router, cloud NAT GW
Firewall the network boundary the whole network iptables, security group
Load Balancer backend servers no single server overloads ALB/NLB, HAProxy
Reverse Proxy backend servers server identity/topology nginx, Envoy
API Gateway microservices services + the API contract Kong, AWS API Gateway
Facade Pattern a subsystem (in code) subsystem internals a *Facade class
Same instinct shows up at every layer: put one stable, simple thing in front of something complicated or exposed, and let it absorb the mess. DNS and NAT answer "where is it"; proxies, VPNs, and firewalls answer "who gets through"; load balancers, reverse proxies, and API gateways answer "who answers"; the facade pattern asks the same question one layer further in, inside the code itself.
